# Data Dictionary — BeneathTheMarket

**Document:** `docs/data_dictionary.md`  
**Project:** BeneathTheMarket  
**Purpose:** Reference for MongoDB collections, stored fields, data types, relationships, and validation rules.  
**Database:** Local MongoDB Community Server  
**Python integration:** PyMongo  
**Market data source:** `yfinance`  
**Schema status:** Proposed — confirm against the implemented application before treating any field as final.

## 1. Purpose and Scope

This document defines the data contract for BeneathTheMarket. It describes the structure and meaning of the records stored in MongoDB, including market observations, company metadata, analytical results, forecasts, model evaluations, and data-refresh records.

It covers:

- MongoDB collection names and purposes.
- Field names, data types, and required status.
- Field constraints and validation expectations.
- Relationships between collections.
- Indexing and data-quality requirements.
- Schema evolution and consistency between the notebook and application.

Detailed system architecture belongs in `docs/architecture.md`. Model comparison methodology belongs in `docs/evaluation_protocol.md`.

## 2. Database Conventions

### 2.1 Database and collections

Use a single local MongoDB database for the project. The database name should be defined centrally in the project configuration rather than repeated throughout the codebase.

| Setting | Convention |
|---|---|
| MongoDB deployment | Local MongoDB Community Server |
| Connection | Configurable local MongoDB URI |
| Python driver | PyMongo |
| Collection naming | Lowercase `snake_case` |
| Field naming | Lowercase `snake_case` |
| Document identifier | MongoDB-generated `_id` unless a specific identifier is required |
| Date and time | BSON `Date` for timestamps |
| Numeric market values | BSON `Double` or `Decimal128`, used consistently |
| Counts and whole-number values | BSON `Int32` or `Int64`, as appropriate |
| Missing optional values | `null` or an omitted field, according to the field definition |
| Source | Explicitly record provenance where necessary |

The default local connection URI may be `mongodb://localhost:27017`. Keep connection details configurable and do not commit credentials or private configuration values.

### 2.2 Required versus optional fields

- **Required:** Must be present for the document to be considered valid.
- **Conditional:** Required when the associated feature or record type is used.
- **Optional:** May be omitted when unavailable or not applicable.

A field being optional does not mean that its absence should be silently replaced with an invented value.

### 2.3 Timestamp conventions

Store timestamps as BSON `Date` values, preferably in UTC. Store the market observation date separately from the timestamp at which the record was retrieved or processed.

For date-based market observations, use a consistent representation of the trading date. Do not treat a trading date as equivalent to a data-retrieval timestamp.

## 4. `market_data`

### Purpose

Stores market observations retrieved through `yfinance`. Each document represents one ticker's market observation for one trading date.

### Field definitions

| Field | Type | Required | Description and constraints |
|---|---|---|---|
| `_id` | ObjectId | No — generated by MongoDB | Unique document identifier. |
| `ticker` | String | Yes | Canonical ticker symbol used by the application. Store consistently, for example, `AAPL`. |
| `observation_date` | Date | Yes | Trading date associated with the observation. |
| `open` | Double or Decimal128 | Conditional | Opening price, when supplied by the source. |
| `high` | Double or Decimal128 | Conditional | Highest recorded price for the observation period. |
| `low` | Double or Decimal128 | Conditional | Lowest recorded price for the observation period. |
| `close` | Double or Decimal128 | Conditional | Closing price for the observation period. |
| `adj_close` | Double or Decimal128 | Conditional | Adjusted closing price, if returned by the source. |
| `volume` | Int64 | Conditional | Reported trading volume, when available. |
| `dividends` | Double or Decimal128 | Optional | Dividend value when provided by the selected source response. |
| `stock_splits` | Double or Decimal128 | Optional | Stock-split value when provided by the selected source response. |
| `source` | String | Yes | Data provider identifier; expected value is `yfinance`. |
| `fetched_at` | Date | Yes | Time when the observation was retrieved or refreshed. |
| `updated_at` | Date | Conditional | Time when the stored document was last updated, if maintained separately. |

**Implementation notes**

- Validate the actual columns returned by `yfinance` before mapping them into MongoDB.
- Adjusted-close and corporate-action fields can vary with the retrieval configuration and available source data. Do not assume every response contains them.
- If the selected retrieval method does not return `adj_close`, omit the field rather than fabricating a value.
- Choose one numeric representation and apply it consistently across ingestion, storage, and analysis.
- Historical records should be upserted using the chosen unique observation key so repeated retrievals do not create duplicate records.

### Recommended unique key

Use a unique compound index on:

`(ticker, observation_date)`

This makes one document the canonical observation for a given ticker and trading date. If the implementation deliberately stores multiple intervals or observation types, extend the key to include the relevant interval or type.

### Validation rules

- `ticker` must be a non-empty string.
- `observation_date` must be a valid date.
- Price values must be numeric and finite when present.
- `volume` must be a non-negative integer when present.
- Where all OHLC fields are available, verify that `high` is not below `low`, and that the open and close values fall within the high–low range, allowing for documented source-specific exceptions.
- Do not interpret a missing observation as a zero-price observation.
- Repeated refreshes must not create duplicate ticker/date records.

## 5. `company_metadata`

### Purpose

Stores the reference information used to identify companies and group them for cross-company analysis.

### Field definitions

| Field | Type | Required | Description and constraints |
|---|---|---|---|
| `_id` | ObjectId | No — generated by MongoDB | Unique document identifier. |
| `ticker` | String | Yes | Canonical ticker symbol; unique within the project universe. |
| `company_name` | String | Yes | Display name of the company. |
| `category` | String | Yes | Project-defined category used for filtering and comparisons. |
| `exchange` | String | Optional | Exchange identifier, if available and verified. |
| `currency` | String | Optional | Currency associated with the market data, when available. |
| `source` | String | Yes | Source or method used to obtain the metadata. |
| `retrieved_at` | Date | Conditional | Retrieval time if the metadata is sourced dynamically. |
| `updated_at` | Date | Conditional | Last metadata update time, if maintained. |

**Implementation notes**

- Define and document a controlled list of categories rather than using inconsistent free-text labels.
- Treat ticker symbols as identifiers, not as guaranteed permanent identifiers for a business.
- Do not infer an exchange or currency when the source does not support the value.
- Keep metadata provenance clear, especially if fields come from different sources.

### Recommended unique key

Use a unique index on `ticker`.

### Validation rules

- `ticker`, `company_name`, and `category` must be non-empty strings.
- Every ticker used in market-data ingestion should map to an entry in the project universe.
- Category values must follow the project's controlled vocabulary.
- Metadata updates must not create duplicate entries for the same ticker.

## 6. `analysis_results`

### Purpose

Stores analytical outputs that the project chooses to persist, including historical statistics, risk summaries, regime-related results, and cross-company comparisons.

The collection should store reproducible results and their relevant context, not entire temporary DataFrames or arbitrary application state.

### Field definitions

| Field | Type | Required | Description and constraints |
|---|---|---|---|
| `_id` | ObjectId | No — generated by MongoDB | Unique document identifier. |
| `analysis_type` | String | Yes | Identifier for the analysis performed, such as `risk_summary` or `cross_company_comparison`. |
| `tickers` | Array of String | Yes | Tickers covered by the analysis; must contain at least one ticker. |
| `period_start` | Date | Conditional | Beginning of the analysis period, when period-based. |
| `period_end` | Date | Conditional | End of the analysis period, when period-based. |
| `parameters` | Document | Yes | Parameters needed to describe the analysis, such as selected period or analysis configuration. |
| `results` | Document or Array | Yes | Structured analytical output. Its internal schema depends on `analysis_type`. |
| `input_data_cutoff` | Date | Yes | Latest observation cutoff used to generate the result. |
| `generated_at` | Date | Yes | Time when the analysis was generated. |
| `schema_version` | String | Yes | Version of the stored result schema. |

**Implementation notes**

- Use a controlled set of `analysis_type` values.
- Document the structure of `results` for every supported analysis type.
- Store numeric results as numeric values rather than formatted display strings.
- Keep display formatting in the application layer.
- If results are inexpensive to reproduce and do not need persistence, they need not be stored in this collection.

### Validation rules

- `tickers` must be an array of non-empty ticker strings.
- Where both period dates are supplied, `period_start` must not be later than `period_end`.
- `input_data_cutoff` must represent the data actually used, not the current time by default.
- `results` must conform to the schema defined for its `analysis_type`.
- Store enough parameters and timestamps to distinguish analyses produced with different inputs.

## 7. `predictions`

### Purpose

Stores model-generated forecasts so that predictions can be inspected, compared with later observations, and associated with the model and input data that produced them.

A prediction is an estimate, not a guarantee of future market performance.

### Field definitions

| Field | Type | Required | Description and constraints |
|---|---|---|---|
| `_id` | ObjectId | No — generated by MongoDB | Unique document identifier. |
| `ticker` | String | Yes | Ticker to which the forecast applies. |
| `target` | String | Yes | Forecast target, such as a closing price or return. |
| `forecast_origin` | Date | Yes | Timestamp or observation cutoff at which the forecast was generated. |
| `target_date` | Date | Conditional | Target trading date, when the forecast concerns a specific date. |
| `horizon` | Document | Yes | Forecast horizon, including its unit and value. |
| `predicted_value` | Double or Decimal128 | Yes | Numeric forecast for the declared target. |
| `model_name` | String | Yes | Stable identifier for the model used. |
| `model_version` | String | Yes | Model version or experiment identifier. |
| `input_data_cutoff` | Date | Yes | Latest observation permitted in the forecast inputs. |
| `generated_at` | Date | Yes | Time the prediction was produced. |
| `parameters` | Document | Optional | Relevant forecast configuration, where required for interpretation. |
| `schema_version` | String | Yes | Version of the prediction document schema. |

**Implementation notes**

- Define the meaning and units of every supported `target`.
- Define `horizon` consistently; for example, a value of `5` must not be ambiguous between calendar days and trading days.
- Store the forecast origin and input cutoff so that a forecast can be checked for accidental future-data leakage.
- If a model produces multiple output values, either store them using a documented structured output schema or create separate records with an unambiguous target identifier.
- Keep prediction records distinguishable by ticker, target, forecast origin, horizon, model, and model version.

### Validation rules

- `ticker`, `target`, `model_name`, and `model_version` must be non-empty strings.
- `predicted_value` must be numeric and finite.
- The horizon must have a positive, documented value and a recognized unit.
- `input_data_cutoff` must not be later than the information cutoff permitted by the forecasting protocol.
- A `target_date`, when present, must be compatible with the declared forecast origin and horizon.
- Predictions generated by different model versions must remain distinguishable.

## 8. `model_evaluations`

### Purpose

Stores model experiment metadata and evaluation results for comparisons across machine-learning and deep-learning approaches.

The collection should record the evaluation context and results. Detailed procedures for chronological splitting, baselines, leakage prevention, and metric interpretation belong in `docs/evaluation_protocol.md`.

### Field definitions

| Field | Type | Required | Description and constraints |
|---|---|---|---|
| `_id` | ObjectId | No — generated by MongoDB | Unique document identifier. |
| `experiment_id` | String | Yes | Unique identifier for the experiment. |
| `model_name` | String | Yes | Stable model identifier. |
| `model_family` | String | Yes | Model family or broad approach classification. |
| `target` | String | Yes | Prediction target evaluated by the experiment. |
| `tickers` | Array of String | Yes | Tickers included in the evaluation. |
| `evaluation_period_start` | Date | Conditional | Beginning of the evaluation period. |
| `evaluation_period_end` | Date | Conditional | End of the evaluation period. |
| `data_cutoff` | Date | Yes | Latest observation available to the experiment, as defined by its evaluation protocol. |
| `split_configuration` | Document | Yes | Description of the training, validation, and test split configuration. |
| `metrics` | Document | Yes | Metric names and their numeric results. |
| `status` | String | Yes | Experiment state, using a controlled vocabulary. |
| `model_version` | String | Yes | Version or identifier for the evaluated model. |
| `started_at` | Date | Conditional | Experiment start time, if tracked. |
| `completed_at` | Date | Conditional | Experiment completion time, if completed and tracked. |
| `schema_version` | String | Yes | Version of the evaluation record schema. |

**Implementation notes**

- `metrics` must use consistent metric names and numeric values for comparable experiments.
- The meaning and units of each metric must be documented in the evaluation protocol.
- Preserve the split configuration so evaluation results can be interpreted correctly.
- Do not compare results as if they were directly equivalent when targets, data periods, or evaluation procedures differ.
- If an experiment fails, record its status and relevant failure summary only if the implementation supports this; do not represent failed runs as completed evaluations.

### Validation rules

- `experiment_id` must be unique.
- `tickers` must contain valid, non-empty strings.
- Metric values must be numeric and finite when a metric is successfully calculated.
- `status` must use documented values, for example `running`, `completed`, or `failed`, if those states are implemented.
- Completion timestamps must be consistent with the recorded experiment status.
- Evaluation data must comply with the project's chronological validation and leakage-prevention rules.

## 9. `refresh_status`

### Purpose

Records the execution outcome of data-refresh jobs, allowing the application and notebook to inspect refresh history and identify ingestion problems.

A record describes a refresh attempt; it does not prove that a scheduled refresh is continuously running.

### Field definitions

| Field | Type | Required | Description and constraints |
|---|---|---|---|
| `_id` | ObjectId | No — generated by MongoDB | Unique document identifier. |
| `job_id` | String | Yes | Unique identifier for the refresh attempt. |
| `source` | String | Yes | Data provider; expected value is `yfinance`. |
| `tickers` | Array of String | Yes | Tickers included in the refresh attempt. |
| `started_at` | Date | Yes | Time the refresh began. |
| `completed_at` | Date | Conditional | Time the refresh finished, when available. |
| `status` | String | Yes | Refresh outcome using a controlled vocabulary. |
| `records_inserted` | Int64 | Conditional | Number of new records inserted, if tracked. |
| `records_updated` | Int64 | Conditional | Number of existing records updated, if tracked. |
| `records_processed` | Int64 | Conditional | Total number of records processed, if tracked. |
| `error_summary` | String | Optional | Concise failure description without secrets or sensitive configuration. |

**Implementation notes**

- Create a record for each refresh attempt.
- Update the record when the attempt completes if the chosen job design supports it.
- Distinguish partial success from complete success if partial outcomes are possible.
- Do not store API credentials, environment secrets, or complete sensitive exception dumps in `error_summary`.
- Record counts should follow a documented counting convention.

### Validation rules

- `job_id` must be unique.
- `tickers` must be an array of non-empty strings.
- Any stored record counts must be non-negative integers.
- `completed_at` must not precede `started_at`.
- `status` must use the implemented, documented set of values.
- Failed attempts should remain distinguishable from successful attempts.

## 10. Relationships Between Collections

MongoDB does not require relational foreign keys by default. BeneathTheMarket should maintain logical relationships through consistent identifiers.

| Source collection | Field | Related collection | Relationship |
|---|---|---|---|
| `market_data` | `ticker` | `company_metadata` | Many observations belong to one ticker entry. |
| `analysis_results` | `tickers` | `company_metadata` | An analysis references one or more companies. |
| `predictions` | `ticker` | `company_metadata` | A prediction references a company. |
| `model_evaluations` | `tickers` | `company_metadata` | An evaluation covers one or more companies. |
| `refresh_status` | `tickers` | `company_metadata` | A refresh attempt covers one or more companies. |

### Relationship requirements

- Use the same canonical ticker representation throughout the project.
- Validate that referenced tickers belong to the configured project universe.
- Do not rely on company names as identifiers.
- Preserve timestamps and model identifiers needed to trace derived records back to their inputs and experiment context.
- Avoid copying full market-data histories into analysis, prediction, or evaluation documents. Store references and concise derived outputs instead.

## 11. Indexing Guidelines

Create indexes according to actual query patterns. The following are recommended starting points, not a claim that the indexes have already been implemented.

| Collection | Recommended index | Purpose |
|---|---|---|
| `market_data` | Unique `(ticker, observation_date)` | Prevent duplicate daily observations and support ticker/date queries. |
| `market_data` | `(observation_date, ticker)` if needed | Support date-oriented cross-company queries. |
| `company_metadata` | Unique `(ticker)` | Ensure one metadata entry per ticker. |
| `analysis_results` | `(analysis_type, generated_at)` | Find recent results of a particular analysis type. |
| `predictions` | `(ticker, target, forecast_origin)` | Retrieve forecasts for a ticker and target over time. |
| `model_evaluations` | Unique `(experiment_id)` | Prevent duplicate experiment identifiers. |
| `model_evaluations` | `(model_name, target, status)` if needed | Filter evaluations by model, target, and status. |
| `refresh_status` | Unique `(job_id)` | Identify individual refresh attempts. |
| `refresh_status` | `(started_at, status)` | Inspect refresh history and outcomes. |

Before adding indexes, check whether an equivalent index already exists and measure the performance benefit. Indexes add storage and write overhead.

## 12. Data Quality and Validation

Apply validation at ingestion and before persisting derived results.

### Market-data quality

- Confirm that the ticker is part of the configured company universe.
- Validate date and numeric types.
- Reject non-finite numerical values.
- Check OHLC consistency when all relevant fields are present.
- Distinguish absent source values from actual zero values.
- Use upserts and the unique observation key to handle repeated retrievals.
- Track the retrieval timestamp separately from the trading date.

### Derived-data quality

- Record the input-data cutoff for predictions and analytical results.
- Use consistent units and target definitions.
- Validate the shape of analysis outputs and model metrics.
- Keep experiment identifiers and model versions stable enough to identify results.
- Avoid persisting results that cannot be associated with their inputs or configuration.

### Refresh quality

- Record the outcome of each refresh attempt.
- Track processed, inserted, and updated counts only when those counts are measured reliably.
- Distinguish source unavailability, missing observations, and application errors.
- Do not treat an empty source response as proof that all market observations are absent.

## 13. Schema Versioning and Evolution

Use `schema_version` for collections whose documents may evolve, particularly `analysis_results`, `predictions`, and `model_evaluations`.

For other collections, add an explicit schema version if the implementation requires migration or compatibility management.

When changing a schema:

1. Update this document.
2. Update ingestion, validation, and serialization code.
3. Update affected notebook and application queries.
4. Decide whether existing documents require migration.
5. Add or update tests for the changed schema.
6. Verify that both the notebook and Streamlit application can read the intended document versions.

Do not silently rename or reinterpret stored fields without considering existing documents and dependent queries.
